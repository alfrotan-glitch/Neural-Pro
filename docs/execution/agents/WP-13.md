## 1. Objective

Resolve the twelve **RUNTIME-UNKNOWN** capability items and the six frame-specific unknowns
(`P-01…P-06`) **by execution inside Google AI Studio**, and produce the compatibility gate
evidence for **two independent certification contexts**:

| Context | Name | Meaning |
|---|---|---|
| **Context P** | **AI Studio Preview / Build-mode runtime** | the app running inside the AI Studio preview frame (dev container) |
| **Context U** | **Published AI Studio application runtime** | the app running at its published URL (`*.ai.studio` / AI Studio-provisioned service) |

Results are **never** merged into one undifferentiated verdict:
`G-31 = PASS` **only if** `G-31-P = PASS` **AND** `G-31-U = PASS`.

Until this WP runs, no statement about AI Studio compatibility is evidence — it is reasoning,
and the architecture forbids converting uncertainty into assumption (ADR-000).

## 2. Context

The application **is** an AI Studio app:

* `metadata.json` — app manifest with `majorCapabilities: ["MAJOR_CAPABILITY_SERVER_SIDE_GEMINI_API"]`
  and `requestFramePermissions: []`;
* `README.md` — "View your app in AI Studio: https://ai.studio/apps/bdf5ad65-6c0d-48f4-8ba5-1e1a337f20ce";
* `.env.example` — AI Studio-injected `GEMINI_API_KEY` and `APP_URL`;
* `vite.config.ts` — `DISABLE_HMR`, `allowedHosts` for the proxied host.

The previous blueprint never inspected these and treated the publish path as the target. This WP
produces the missing runtime evidence.

## 3. Scope

1. Run the capability probe in both contexts; record `CapabilityReport[]`.
2. Resolve `P-01…P-06` with **explicit evidence classifications** (§5).
3. Execute **AS-01…AS-16** independently in **Context P** and **Context U**.
4. Update the capability classification table: move each `C` item to `A`, `B` or `D` **with
   runtime evidence**. Items that remain unresolved stay `C` with a named owner — never
   promoted silently.
5. Feed findings back (each unknown already has a pre-committed branch in the frozen design).
6. **Observe only.** No product defect is fixed here (§11).

## 4. Deterministic fixture (mandatory)

WP-13 must commit and use a **deterministic** fixture. It is a *runtime verification* fixture,
not a feature demo.

### 4.1 Prohibited fixture inputs

| Prohibited | Why |
|---|---|
| remote media URLs (`commondatastorage.googleapis.com`, `soundhelix.com`, …) | network-dependent, non-reproducible |
| previously generated Blob URLs | dead across contexts/sessions |
| random waveform generation (`Math.random()`) | non-deterministic (D-024/R-024) |
| current timestamps / `Date.now()` in content | non-reproducible hashes |
| unstable AI output | model output is not a stable baseline |
| external media hosting | offline-incompatible |
| previous `localStorage` / IndexedDB state | contaminates persistence criteria |
| any other previously existing browser state | same |

### 4.2 Required fixture content (where practical)

| Item | Purpose |
|---|---|
| a short **MP4** | video decode, seek, encode |
| a short **MP3** (or WAV) | audio decode, duration measurement, audio render |
| a **PNG** | image decode, cover-scaling/clipping cases |
| **sequential clips** (≥ 3 on one track, non-overlapping active windows) | proves export independence from the Preview DOM (AS-10) |
| a **transformed clip** (non-uniform `scaleX ≠ scaleY` **and** `rotation ≠ 0`) | exercises the D-004/parity path |
| **multiple aspect-ratio cases** (16:9, 4:3, 9:16, ≥ 2.39:1) | exercises the D-005 clipping path |
| **captions** (fixed content, fixed timings, fixed fps) | caption layer + timecode parity |
| **audio track(s)** with known duration | duration authority (INV-011) |
| representative export content (text/overlay/background layers) | renderer coverage |
| a **content hash** recorded at build time | proves the fixture is byte-identical across runs |

The fixture is generated by a committed script (`tests/fixtures/buildDeterministicFixture.*`)
that is seeded, byte-stable and verifiable by hash. **A fixture that is not byte-stable is not a
fixture.**

## 5. Evidence classification system (mandatory on every observation)

Every runtime observation carries **exactly one** class:

| Class | Meaning |
|---|---|
| **EXECUTED-RUNTIME** | directly observed inside the real AI Studio runtime |
| **EXECUTED-BROWSER** | directly observed in the browser, but not sufficient to establish server/runtime behaviour |
| **STATIC-EVIDENCE** | derived from repository/source inspection |
| **DOCUMENTED-PLATFORM** | supported by current official Google documentation |
| **INFERRED** | reasoned conclusion that is **not** executable evidence |
| **BLOCKED** | could not be tested because required runtime access/capability was unavailable |
| **UNKNOWN** | evidence is insufficient |

**Rule:** a compatibility **PASS must not** be based solely on `INFERRED`, `STATIC-EVIDENCE` or
`DOCUMENTED-PLATFORM` where the gate requires actual runtime execution.

### 5.1 Anti-false-PASS rule (normative)

> **No compatibility criterion may be promoted to PASS merely because the repository
> architecture appears compatible, Google documentation describes the capability, or a local
> environment successfully executes it.**
>
> For runtime-dependent criteria, PASS requires **executable evidence in the target context**.

## 6. Unknown-resolution contract

### `P-01` — Export artifact delivery (corrected)

**Question:** can the AI Studio Preview and the Published App successfully **initiate and
complete export artifact delivery to the user/browser download surface**?

**This criterion must NOT require direct operating-system filesystem visibility** unless that
capability is explicitly exposed by the target runtime.

`P-01` distinguishes four separate observations, each recorded independently:

| Sub-observation | Question | Observable evidence |
|---|---|---|
| `P-01.a` **artifact produced** | was the export artifact successfully produced in-browser? | artifact `Blob` exists; byte size > 0; decodes to the expected frame count and duration |
| `P-01.b` **delivered to browser/user** | was the artifact successfully handed to the browser download surface? | a download was initiated (browser download event / `beforeunload`-safe download UI), or an explicit save affordance completed |
| `P-01.c` **download permitted** | does the context permit the download mechanism? | download completes, or is blocked/refused with an observable reason (CSP/sandbox/permission) |
| `P-01.d` **direct filesystem visibility** | is host filesystem visibility exposed at all? | recorded as `NOT-EXPOSED` / `EXPOSED`; **never** a PASS condition |

**PASS condition for `P-01`:** `P-01.a` **and** `P-01.b` observed with `EXECUTED-RUNTIME` or
`EXECUTED-BROWSER` evidence. `P-01.d` is informational only.

### `P-02` — Storage availability/partitioning in the frame
Probe `indexedDB.open()`, a round-trip write/read, and `navigator.storage.estimate()`; verify
survival across reload **and** across a new session in the same context. Classify per §5.

### `P-03` — WebCodecs / OfflineAudioContext (strengthened)

Three repeated runs are **not** evidence of throttling. `P-03` is decomposed into ten
sub-observations, each recorded separately:

1. **API availability** — `VideoEncoder.isConfigSupported` matrix; `typeof OfflineAudioContext`.
2. **Initialization success** — encoder/decoder construction, `AudioContext` creation.
3. **Representative workload** — a short encode (≥ 300 frames) completing correctly.
4. **Sustained workload** — a longer encode where practical; record duration and any
   degradation.
5. **Completion/failure behaviour** — success, typed failure, silent stall, or crash.
6. **Timing measurements** — wall-clock per phase, recorded for both contexts.
7. **Resource behaviour** — JS heap, `performance.memory` where available, encoder queue depth.
8. **Preview vs Published comparison** — the same measurements in both contexts.
9. **Runtime-imposed throttling or timeout** — background-tab behaviour, long-task throttling,
   any observable ceiling.
10. **If throttling cannot be measured, mark it `UNKNOWN`.**

**Do not infer absence of throttling from a small successful test.**

### `P-04` — CSP / frame policy restrictions
Capture CSP report events and console violations during boot, media decode and export.

### `P-05` — Proxy behaviour for long requests and cancellation
Time an intentionally slow endpoint; record whether the client observes a timeout, a proxy
error, or a hang; record `AbortController` propagation behaviour.

### `P-06` — Preview vs Published differences (measurable dimensions)

Record each dimension in **both** contexts and compare:

| # | Dimension |
|---|---|
| 1 | boot success |
| 2 | server availability (`/api/health`) |
| 3 | Gemini access (`/api/health/ai`, one real operation) |
| 4 | browser APIs (capability report) |
| 5 | storage (availability, quota, persistence across reload) |
| 6 | media loading (import + decode + measured duration) |
| 7 | export (success, frame count, duration, artefact hash) |
| 8 | download / delivery behaviour |
| 9 | request duration (per-operation latency) |
| 10 | cancellation (terminal state reached, time taken) |
| 11 | CSP (violations observed) |
| 12 | network behaviour (egress allowed/denied to which hosts) |
| 13 | capability report (server-side, when WP-07 exists) |

**If a material difference exists, the two contexts are certified separately and the difference
is recorded as a finding** (it does not silently become one verdict).

## 7. Corrected criteria: AS-13, AS-14, AS-16

### AS-13 — Native execution capability **investigation** (corrected)

**AS-13 must not presuppose the answer.** It is a runtime capability investigation.

Determine, with recorded evidence, whether the AI Studio target runtime permits:

1. native binaries,
2. subprocess execution (`spawn` / `child_process`),
3. FFmpeg (present? installable? executable?),
4. packaged binary execution (e.g. an npm-shipped binary),
5. executable permissions (`chmod +x` / preserve-on-install),
6. server-side media processing of any kind.

Then **classify the result A / B / C / D** per the classification table, with the evidence class
from §5.

* If the runtime **supports** a capability the frozen architecture forbids → record it as
  **informational**; the architecture decision stands (ADR-016) unless an ADR changes it.
* If the current Neural-Pro architecture **uses** a capability the runtime does **not** support →
  **create a defect with evidence and assign it to the owning WP** (for the current code: WP-01).
* **Do not manufacture a PASS because a grep found no `spawn`.** A static grep is
  `STATIC-EVIDENCE` and cannot satisfy a runtime criterion on its own.

### AS-14 — No **unauthorised external media-processing** dependency (corrected)

**AS-14 does not require zero external services.** Neural-Pro legitimately uses Gemini for AI
workflows (podcast script generation, caption generation/refinement, TTS where applicable).

AS-14 must distinguish:

| Category | Definition | Verdict |
|---|---|---|
| **Allowed external dependency** | Gemini / explicitly approved AI API operations, invoked through the server operation allowlist | legitimate, expected |
| **Prohibited hidden dependency** | an unapproved external **media renderer, transcoder, export service, or rendering backend** | must be absent |

**Criterion:** verify that **media export does not depend on an external media-processing or
rendering service**, unless such a dependency is explicitly part of the frozen architecture.

**Evidence required:**
* an inventory of every network destination contacted during a full export
  (DevTools/network log, in both contexts);
* identification of each destination as AI-service / static-asset / media-processing / unknown;
* assertion that no destination performs rendering, transcoding or export for Neural-Pro.

### AS-16 — Capability-denial testability contract (corrected)

"Disable/deny a capability and assert the honest refusal" is valid **only if the capability can
actually be controlled**. AS-16 therefore declares its denial mechanism and classifies the
evidence:

**Permitted denial methods:**
* controlled browser test fixture (e.g. a context that omits the API),
* capability shim / injected `MediaRuntimeCapabilities` adapter,
* injected unavailable capability via a deterministic test adapter,
* browser context policy (permissions policy / CSP override in a test harness),
* server capability override (when WP-07's endpoint exists).

**Evidence classification for AS-16:**

| Class | Meaning |
|---|---|
| **RUNTIME-DENIED** | the actual runtime/browser denied the capability |
| **TEST-INJECTED** | the capability was made unavailable through a controlled test mechanism |
| **NOT-EXECUTABLE** | the environment provides no legitimate mechanism to deny the capability |

* **AS-16 may PASS** on `RUNTIME-DENIED` or `TEST-INJECTED` evidence — the purpose is to verify
  that the application **fails honestly** when a required capability is unavailable.
* If AS-16 is **NOT-EXECUTABLE**, record that fact. **Do not fabricate a runtime result.**
* Any claim labelled `RUNTIME-DENIED` that was actually produced by a test shim is a **false
  evidence class** and invalidates the criterion.

## 8. Procedure (ordered, corrected)

### Phase 0 — Preparation (context-independent)
0.1 Build the deterministic fixture (§4); record its content hash.
0.2 Confirm the WP-00 probe harness and report schema exist. (**HARD dependency**)
0.3 Check whether WP-07's `/api/runtime/capabilities` exists. If yes → plan to consume it. If no
    → record server-side capability evidence as *unavailable* and continue. **(not blocking)**
0.4 Confirm AI Studio access and the Gemini key in Secrets. If unavailable → Stage C is
    **BLOCKED** with a named owner.

### Phase 1 — Context P (AI Studio Preview)
1. Open the app in **Build mode**; record the app id and the dev-container notice.
2. Probe: browser-side `MediaRuntimeCapabilities`; if available, `GET /api/runtime/capabilities`.
3. **AS-01** boot — screenshot + console; assert zero uncaught errors.
4. **AS-02** boundary — `/api/health`, `/api/health/ai`; save responses.
5. **AS-03** Gemini — one real `generatePodcastScript` + one `generateSpeech`; assert
   schema-valid, **non-simulated**; record `requestId` and latency.
6. **AS-04** secret exposure — fetch every JS asset; assert no key material.
7. **AS-05/06** media — import the fixture MP4/MP3/PNG; assert decode and **measured** duration.
8. **AS-07** timeline — add/trim/move; undo/redo; assert `totalDuration`.
9. **AS-08** persistence — save → reload → assert media resolves (resolves `P-02`).
10. **AS-09 + P-01** export — export the fixture; **verify artifact integrity; verify
    browser/user delivery behaviour; record exactly what is observable in the AI Studio
    context.** Do **not** assert filesystem visibility.
11. **AS-10** export with the Preview panel closed.
12. **AS-11** cancellation — cancel at each of the 8 steps; assert terminal state + resources.
13. **AS-12** failures — induce the five failure modes; assert typed non-success and honest UI.
14. **AS-13** native-execution **investigation** (§7).
15. **AS-14** unauthorised external media-processing dependency inventory (§7).
16. **AS-15** delivery — classify `P-01.a…d` (§6).
17. **AS-16** capability denial with a declared mechanism (§7).
18. **P-03** the ten sub-observations; **P-04** CSP; **P-05** proxy/cancellation.

### Phase 2 — Context U (Published App)
19. **Publish** the app (Starter Tier suffices).
20. Repeat steps 2–18 against the published URL, recording evidence **separately**.
21. **P-06** — compare all thirteen dimensions across contexts.

### Phase 3 — Reporting
22. Write `reports/ai-studio-compatibility-<date>.json` with per-criterion, per-context results,
    each carrying status + evidence class + evidence reference + timestamp + context +
    reproducibility result.
23. Derive `G-31-P`, `G-31-U` and `G-31` **mechanically** from the criterion results (§9).
24. Update the capability classification table; file defects with owning WPs.

## 9. G-31 derivation (normative)

For each context, every criterion `AS-01 … AS-16` must record:

* `status` ∈ `PASS` · `FAIL` · `BLOCKED` · `UNKNOWN` · `NOT-APPLICABLE`
* `evidenceClass` (§5)
* `evidenceRef` (artefact path / request id / screenshot)
* `timestamp`
* `context` ∈ `P` · `U`
* `reproducibility` (number of runs, agreement across runs)

Then:

```
G-31-P = PASS  iff every blocking criterion PASSES in Context P
G-31-U = PASS  iff every blocking criterion PASSES in Context U

G-31   = PASS    iff G-31-P = PASS AND G-31-U = PASS
G-31   = FAIL    if executable evidence demonstrates incompatibility
G-31   = BLOCKED if required runtime access/evidence is unavailable
G-31   = UNKNOWN if evidence is incomplete but execution was possible
```

Explicit consequences:

| Situation | Result |
|---|---|
| Preview PASS, Published FAIL | **G-31 = FAIL** |
| Preview PASS, Published not executable | **G-31 = BLOCKED** |
| Either context unavailable | **G-31 = BLOCKED** (unless the gate declares a narrower scope, in writing, with an owner) |

## 10. Acceptance criteria (replaced)

1. `AS-01…AS-16` are **independently recorded for Context P and Context U**.
2. `P-01…P-06` each carry **explicit evidence classifications**.
3. No **resolved** `C` capability remains classified as `C`.
4. Any **unresolved** capability remains `C` with a **named owner**.
5. Every **FAIL** has evidence **and** an owning WP.
6. Every **BLOCKED** item has a concrete blocking reason **and** an owner.
7. **No runtime PASS is based solely on static or documentary evidence.**
8. Preview and Published results remain **separately auditable**.
9. The **fixture is deterministic** (byte-stable, hash recorded).
10. **No product behaviour was modified by WP-13** — the diff contains only `reports/`,
    `tests/ai-studio/**`, `tests/fixtures/**` and docs.
11. The **evidence bundle is committed** with the report.
12. `G-31` is **derived mechanically** from the criterion results, not asserted.

## 11. Failure ownership (normative)

WP-13 observes and records. It does **not** repair product defects.

When a criterion fails, WP-13 performs exactly seven steps and stops:

1. **preserve evidence** (artefact, log, screenshot, request id, timestamp, context);
2. **create or update the defect record** (defect register / risk register with an ID);
3. **identify the owning WP**;
4. **identify the affected invariant** (AS-INV-xx / INV-0xx);
5. **identify severity**;
6. **state whether the architecture requires reconsideration** (and if so, escalate to an ADR
   rather than changing the design inside WP-13);
7. **stop.**

**No defect is fixed inside WP-13.**
