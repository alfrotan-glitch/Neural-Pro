# WP-10 — Recovery & Runtime Certification

**Priority:** P1
**Depends on:** WP-06 and all repair WPs (02–05, 07, 09, 11)
**Blocks:** the `RUNTIME CERTIFIED` claim
**Estimated risk:** Medium

---

## 1. Objective

Implement workflow W5 (Recovery) and **execute** the runtime certification sequence
([../runtime-certification-plan.md](../runtime-certification-plan.md)).

## 2. Scope

1. **`recovery` workflow** per [../../workflows/recovery.md](../../workflows/recovery.md):
   scan, validate, decide (resume / restart / manual), run, cleanup, report.
2. **Heartbeat**: every run writes `lastHeartbeat` (in-memory; persisted every 5 s for long
   runs). Recovery is the only reader allowed to classify a run as dead.
3. **Stale-state reclassification**: non-terminal + no heartbeat ⇒ `expired`; `rendering` with
   no in-flight promise ⇒ `failed` (`INTERNAL`).
4. **Cleanup**: release media pool, revoke tracked object URLs, dispose encoders/muxers, remove
   listeners/timers, drop expired checkpoints, evict orphaned assets (with confirmation).
5. **Unload handling**: on page unload, every run reaches a terminal state (R-032 documented
   limitation: exports do not survive reload — surfaced in the UI).
6. **Certification execution**: Stages A–F of the certification plan, with recorded evidence.

## 10. Acceptance criteria

1. Test #23 and the four recovery tests pass.
2. Every stage of the certification plan has a recorded result: `PASS`, `FAIL`, or `BLOCKED`
   with a named blocker and owner.
3. Stage D (browser) executed with `cases > 0` in the report.
4. Stage E executed **if** egress exists; otherwise recorded BLOCKED with R-030 referenced.
5. Stage F executed; the container boots with `PORT=8080`.
6. The certification report is committed and linked from `docs/README.md`.

## 13. Conflict risks

| Risk | Mitigation |
|---|---|
| Certification reveals new defects | record as `R-0xx` with evidence; route to the owning WP; do not fix inside WP-10 unless it owns the file |
